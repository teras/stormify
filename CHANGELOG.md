# Changelog

Stormify release history.

## [3.0.1] - 2026-10-29

### Migration from 2.6.0

Changes that can affect code written for 2.6.0, and what to do. The entries
below give the details.

**API**
- **`Sp.InOut.input` is now `T?`** (breaking for Kotlin source), and
  `Sp.inOutParam` / `Sp.InOut` / `spInOut` accept `null`. Kotlin code that
  reads `input` as non-null needs `!!` or a null check. JVM binaries are
  unaffected (same erased signature).
- **Native OUT parameters return `null` for SQL `NULL`** where they returned
  `0`. Code that treated `0` as "no value" should test for `null`.
- **The bookkeeping of an entity is no longer public Java API**:
  `get_stormify$stormify()` and the like are gone (they were never meant to
  be called); the values are private fields behind synthetic accessors.
- **A primitive key left at `0` takes the declared sequence's value** on `create`,
  as a `null` key does; code that stored `0` as a real key value with a sequence
  declared assigns it after the insert or drops the sequence.
- **`NamingPolicy` presets are static fields and `StormifyLifecycle.clear()` is a
  static method in Java**: `NamingPolicy.INSTANCE.getCAMEL_CASE()` becomes
  `NamingPolicy.CAMEL_CASE` (likewise the other two), and
  `StormifyLifecycle.INSTANCE.clear()` becomes `StormifyLifecycle.clear()`.
  Kotlin code is unaffected.
- **An exception thrown inside `transaction { }` reaches the caller unchanged**,
  blocking and suspend, top level and nested, where it was wrapped in an
  `SQLException("Unable to execute transaction")` with the original as `cause`.
  Code that caught `SQLException` and read `cause` to find its own exception
  catches that exception directly; code that relied on every failure being an
  `SQLException` catches `Exception`. Database errors are `SQLException`s as before.
- **A cancelled suspend `transaction { }` or `withConnection { }` ends in a
  `CancellationException`**, with the failure of the interrupted statement as
  its cause, where it threw that failure (an `SQLException`). Code that caught
  `SQLException` to notice a cancellation catches `CancellationException`, or
  lets it propagate as structured concurrency expects.

**Mapping (JVM reflection)**
- **`@Entity(name)` is the table name** when there is no `@DbTable(name)` or
  `@Table(name)`. An entity that relied on the class-derived name while
  carrying `@Entity(name = ...)` now maps to that name: add `@Table(name = ...)`
  with the old name, or rename the table.
- **`@SequenceGenerator(sequenceName)` is the sequence**, `name` only when
  `sequenceName` is empty. Entities whose generator and sequence names differ
  now draw keys from `sequenceName`.
- **`@JoinColumn(insertable/updatable = false)` is honored**, and a
  `@DbField` with default values no longer overrides `@Id`,
  `@Column(insertable/updatable = false)` or `@Enumerated(STRING)`. Columns
  that were written although marked so are no longer written.
- **Read-only properties with a backing field are columns**: a `val`, a `var`
  with a private or protected setter, a Java field without setter are loaded
  into their field and written from it (not through the getter). They used to
  fail on load.
- **Computed properties are not columns** (they used to break every statement),
  a read-only delegate other than `db` such as `val x by lazy { }` must be
  marked `@delegate:Transient`, and `val x by db()` must become `var`: both are
  now rejected when the class is first used.

**Annotation processor**
- **Annotations are merged like under reflection.** `@GeneratedValue(strategy =
  IDENTITY)` is now honored (the key is generated by the database); a
  `@Column` without a name no longer erases the name given by `@DbField`, and
  the name comes from the first annotation that sets one; the table name is
  taken from `@DbTable`, then `@Table`, then `@Entity`, whatever their order.
  Entities whose mapping depended on the annotation order, or that declared
  IDENTITY while relying on keys assigned by the application, map differently.
- **`@SequenceGenerator(sequenceName)` is the sequence** here too.
- **A read-only property is a compile error** ("must be a var (or use by
  db())"), as is a read-only delegate without `@delegate:Transient`. Such
  entities did not compile before either, but now the message says what to
  change: use `var`, `by db()`, or mark the property transient. Computed
  properties are skipped, mutable delegates are accepted.

**Serialization**
- **Entities are `java.io.Serializable` on JVM and Android** (`StormifyEntity`,
  `AutoTable`, the `db` and `lazyDetails` delegates), with
  `serialVersionUID = 1`. Frameworks that serialize objects found in a session
  or a cache now serialize entities instead of rejecting them: every field of
  an entity must then be serializable or `@Transient`. A shadow reference
  that was never loaded loads on first access after deserialization, through
  `Stormify.defaultInstance`; without one, the access throws `SQLException`.

**Loading**
- **A reference to a missing row fails on every access**, not once followed by
  an empty entity; its valid siblings keep working. **A failed load is
  retried** on the next access instead of leaving empty fields.
- **`lazyDetails` returns every parent's children** in results larger than 32
  rows, where it returned empty lists beyond the first batch.

**Paged lists and queries**
- **`PagedList` and `PagedQuery` are one class each**, in common code, instead
  of `AbstractPagedList` / `AbstractPagedQuery` with a subclass per platform. Code
  that named the abstract classes names `PagedList` / `PagedQuery`. Both take a
  `KClass`; the Java `Class` constructors are gone.
- **Sorted facets are ordered by when they were sorted**, not by when they were
  added: the `ORDER BY` of a `PagedList` lists the sorted facets in the order their
  sort was set (`sort(path, direction)` or `facet.sort`), and the `ORDER BY` of a
  `PagedQuery` follows the order of the sorts in the `PageSpec`.
- **`sort(path, direction)` throws for a path no facet covers** instead of adding
  a facet.
- **The primary key is appended to every `ORDER BY`** as a tie-breaker (and
  `keySort` sets its direction, ascending by default). The generated SQL and
  the order of rows that tie on the facet sorts change. An entity with a
  composite key no longer needs an explicit sort.
- **Constraints are parenthesized** before the facet filters are ANDed to
  them. A constraint containing `OR` that relied on the old precedence must be
  rewritten; most such code was leaking rows by mistake.
- **An empty or blank filter is no filter**, where it matched no row.
- **Filter values include SQL `NULL`** as the last value, shown as
  `FilterSyntax.nullToken` and counted in the size; counted values show it as
  the null token instead of `""`.
- **Enum facet filter values are display names** instead of stored values,
  and an enum facet on an `enumAsString` field compares names.
- **`FilterSyntax.wildcard` is honored**: with a custom wildcard, `*` is a
  plain character. **A null token without letters** (`--`) now means `IS NULL`
  on numeric and temporal facets.
- **`SqlDialect.queryFormatter` takes no page bounds** and returns the paged
  `SELECT` with a `?` for each bound; bind the values of
  `SqlDialect.pageBinds(lowBound, upperBound)` after the arguments of the
  constraints.

**Logging**
- **A NOP SLF4J backend is not used**: the logger moves to the next framework.

**Instances, constants and Java interop**
- **`PagedList` and `PagedQuery` are created only by a `Stormify` instance**:
  `stormify.pagedList<T>()` / `stormify.pagedQuery<T>()`, or the top-level
  `pagedList<T>()` / `pagedQuery<T>()` on the instance a call without one uses (Java:
  `stormify.pagedList(T.class)` / `pagedQuery(T.class)`). The constructors and the
  `PagedList<T>()` / `PagedQuery<T>()` functions are gone, and so are `attach` for
  them and the `StormifyAware` interface; `attach` takes an entity. Both classes are
  final.
- **The scoped `asDefault { }` is removed**, in Kotlin and Java, together with the two
  Java overloads. The default changed for every thread at once, so concurrent callers
  saw each other's instance. A call that names no instance uses the instance of the
  enclosing `transaction { }` or `withConnection { }` (see Fixed), which covers what the
  scoped form was for; elsewhere call the instance itself. `asDefault()` stays.
- **`StormifyJ.getDefault()`** wraps the current default instance and throws an
  `SQLException` when there is none, where it returned `null`. `StormifyJ(stormify)`
  wraps a Kotlin instance and `stormifyJ.stormify` returns it.
- **`CRUDTable<T>`** takes the entity class: `class User : CRUDTable<User>`, and
  `create()` / `update()` return the entity, as every other create and update does.
- **One sort direction, `SortState`**: `SortDir` and `PagedListSort` are gone.
  `PageSpec.sorts` and `PagedListState.sorts` hold `SortState`; `PageSpec.fromJson`
  reads `"ASC"`/`"DESC"` as well as `"ASCENDING"`/`"DESCENDING"`.
- **One name per constant**: `Facet.TEXT`, `Facet.NUMERIC`, ..., `Facet.ASCENDING`,
  `Facet.DESCENDING` are gone; use `Facet.Type.TEXT` ... and `SortState.ASCENDING` /
  `SortState.DESCENDING`.
- **`@DbField(insertable = ...)`** replaces `@DbField(creatable = ...)`, the word JPA,
  `updatable` and `FieldInfo.isInsertable` already use; `PropertyMeta.isCreatable` is
  `isInsertable`.
- **`InputParser`, `Converter` and the row callback of `forEachStreaming` (`RowConsumer`)
  are `fun interface`s.** Java implements them with plain lambdas. In Kotlin a lambda
  assigned to a property names the type: `facet.converter = Converter { ... }`,
  `stormify.inputParser = InputParser { ... }`.
- **`KdbcDataSource(url)` exists on the native targets only**; on the JVM it threw at
  run time. Use `JdbcDataSource` on the JVM and `AndroidDataSource` on Android.
- **`PoolClosedException` and `PoolAcquireTimeoutException` are `SQLException`s**, like
  every other database error; `SQLException` is open for them.
- **Removed**: `TypeUtils.register` (use `TypeConversion.register`), `TypeUtils.err`,
  the parser classes behind the filters (`OrderedQuery`, its nodes, `FieldPath`,
  `TextQuery.renderAst`), now internal. The Kotlin top-level functions are no longer
  visible from Java, where `StormifyJ` is the API.

### Added
- **`TableInfo.getIdValues(entity)` is public.** Returns the primary key values
  of an entity in the order of `primaryKeys`, one per key column for a composite
  key, so generic code (caches, equality, audit, `findById` with the key of an
  object) reads the key without reflection, also on native targets.
- **`Sp.InOut` accepts a `NULL` input.** `Sp.inOutParam(type, null)`,
  `Sp.InOut(type, null)` and `spInOut<T>(null)` send SQL `NULL` into an INOUT
  parameter while `type` still declares it; until now the input was
  non-nullable and a Java `null` failed the parameter null check. On JDBC the
  `NULL` is bound with the SQL type the parameter was registered with, which
  Oracle requires (an untyped `NULL` gave "Parameter Type Conflict"). The
  `input` property is now `T?`.
- **`keySort` on `PagedList` and `PagedQuery`.** Sets the direction of the
  primary key in the generated `ORDER BY`, both when no facet sorts and as the
  tie-breaker after the facet sorts. Defaults to `ASCENDING`, the previous
  order. Structural like the facets, so it is not part of `PagedListState`.
- **`StormifyJ` exposes the remaining instance settings.** Java callers can now
  set `sqlDialect` (for a data source whose dialect cannot be detected, such as
  one behind a proxy), `cursorFetchSize`, `filterSyntax` and `inputParser`, and
  read `dataSource`. Before, these were reachable only from Kotlin, and the Java
  `setInputParser` example in the PagedList guide did not compile.
- **Entities are `java.io.Serializable` on JVM and Android.** `StormifyEntity`
  (and so `AutoTable`) and the `db` delegate implement the new
  `PlatformSerializable` marker, which is `java.io.Serializable` on JVM and
  Android and an empty interface on native, and the `lazyDetails` delegate is
  serializable on JVM and Android. Loaded values and already read `lazyDetails` lists are kept, a shadow
  reference that was never loaded loads its row on first access after
  deserialization through `Stormify.defaultInstance`, and the `Stormify`
  instance and sibling group are not serialized. `PagedList` and `PagedQuery`
  stay non-serializable.
- **Fixed serialization version.** `StormifyEntity`, `AutoTable`, the `db`
  delegate and the JVM `lazyDetails` delegate declare `serialVersionUID = 1`,
  so entities serialized by one release stay readable by the next as long as
  their serialized state is compatible, instead of failing on a version
  computed from the class layout.
- **Fluent declaration of a `PagedList`.** `facet(...)`, `sort(path, direction)`,
  `distinct()`, `keySort(direction)` and `constraints(sql, args...)` configure the
  list like `addFacet`, `Facet.sort`, `isDistinct`, `keySort` and `setConstraints`,
  and return the list,
  so a list can be declared in one chained expression from Kotlin and Java. The
  `facet` overloads mirror `addFacet` (typed or dot-notation paths, explicit type,
  enum map). `sort(path, direction)` sorts by that exact path, also inside a facet
  with several paths; the facet must have been declared. The existing methods are
  unchanged.
- **`stormify.pagedList<T>()` / `stormify.pagedQuery<T>()`** (Java:
  `stormify.pagedList(T.class)` / `pagedQuery(T.class)`) create a `PagedList` or
  `PagedQuery` that works on that instance; the top-level `pagedList<T>()` /
  `pagedQuery<T>()`, like `findById<T>()`, create one on the instance a call without one
  uses.
- **The fluent declaration of a `PagedQuery`**: `facet(alias, ...)`, `distinct()`,
  `keySort(direction)` and `constraints(...)`, as on `PagedList`.
- **Java parity**: `details(Class)` on entities, the Java counterpart of
  `by lazyDetails()`, loading through the instance that read the entity and for the
  whole result at once; `getTableInfo(Class<T>)` typed as `TableInfo<T>`; `readCursor` /
  `readRowsCursor` with a per-call `fetchSize`; `@JvmOverloads` on `FilterSyntax` and
  `PagedListState`.
- **`TextFolding`, the text folding of case-insensitive facet filters.**
  `Stormify.textFolding` (and `StormifyJ.setTextFolding`) decides how a
  case-insensitive text filter folds the column in SQL and the typed text, and how
  an enum filter matches display names, so an application can match without accents
  or with its own normalization. The default, `TextFolding.DEFAULT`, is the previous
  behavior: `LOWER`/`ILIKE` per dialect and lowercase on the client side.
  `TextQuery.parseAndRender` takes an optional `folding`. The folding applies to
  the literal pieces between wildcards, before escaping, so it cannot remove a
  wildcard.
- **`Facet.getFilterRawValues()`**, the distinct values of a facet as they come
  from the database instead of as text, for callers that format them themselves.
  Unlike `getFilterValues()`, it lists the values of every path of a facet with
  several paths (SQL `UNION`), includes SQL `NULL` as a last `null` element, and
  converts the values to the field type. All paths of the facet must have the same
  field type, otherwise it throws `IllegalArgumentException`. Same filtering by
  the other facets, ordering and paging as `getFilterValues()`, which is unchanged.
- **`Stormify.dynamicUpdate`, opt-in update of the changed columns only.** When
  on, entities that extend `StormifyEntity` keep a copy of their column values when
  loaded, and `update` writes only the columns that differ, or nothing when none
  does. Entities without a copy get the full `UPDATE`. Batch updates are grouped
  by the set of changed columns. Mutable values (byte arrays, `java.util.Date`,
  `Calendar`) are copied, so changes made in place are detected. A changed primary
  key gives the full `UPDATE`. Inside a transaction the written values become the
  reference on commit; a rollback (also of a nested savepoint) drops the reference
  of the entities it updated, so their next update is full, also when the flag was
  switched on inside the transaction. An entity with no
  changed column issues no statement, so nothing checks that its row still exists.
  Off by default; also settable through `StormifyJ.setDynamicUpdate`.
- **`Facet.sortPath`**, the path a facet with several paths sorts by. Until now
  such a facet always sorted by its first path; that stays the default. Set by
  `PagedList.sort(path, direction)`, or directly at setup time, including on a
  `PagedQuery`.
- **`PagedList.facetByPath(path)`** returns the facet that has the path among its
  field paths, matching any path of a facet with several, or `null`.

- **`readRows` / `readRowsCursor`: rows by column position.** Each row comes
  back as an `Array<Any?>` of its column values, so columns with the same label
  (`SELECT a.id, b.id ...`) all come back, where a `Map` read keeps one of them.
  Values are converted as for a `Map` read, and the query runs on the active
  transaction's connection. Available on `Stormify` (all targets) and `StormifyJ`.

- **`danglingReferences`: what a reference to a missing row does.** A per
  instance policy (also on `StormifyJ`). `THROW`, the default, is the existing
  behavior: loading the reference throws "No data found". `NULL` makes it read
  as `null`, as with JPA: when a read, a refresh or a lazy load completes, the
  referenced keys are checked with one query per referenced type (on the
  connection of the surrounding transaction, otherwise on one of its own) and
  the properties that point at missing rows are set to `null`, while the other
  references stay lazy. A streaming read hands its rows to the consumer after
  the check. The entity remembers the key and writes it back on update while
  the property stays `null`, so a dangling foreign key is never turned into
  `NULL`; setting the property, to an entity or to `null`, replaces the key.
  Plain classes, which cannot remember it, keep the reference object instead.
  A reference held some other way loads with default values instead of
  throwing. References with a composite key are not checked.

- **`SqlDialect.pageBinds(lowBound, upperBound)`**, the values for the page
  placeholders of `queryFormatter`, in the order the dialect's SQL expects them.

- **A generated reference class defaults to the root path.** `XRef()` builds the
  root path of entity `X`, the same as `Tables.X_`, in annproc and in the Gradle
  plugin; passing a prefix works as before.

### Changed
- **The JVM asks the driver for the class of the column, not of the property.** A
  driver is only sure to produce a column's own class: pgjdbc refuses a `Long` from
  an `int4` or a `String` from a number, ojdbc a `BigInteger` or a `Character`, and
  every driver a `UUID` or a `Character` from a `VARCHAR`. kdbc recovered by reading
  again untyped, but the driver, or the pool wrapping it, could log the refusal first
  (Payara logs each as SEVERE), and each cost a thrown exception. For a column of
  numbers, text or bytes the column's own class is now read and converted, text is
  read with `getString`, and a temporal value of another kind than the column's (a
  date from a timestamp) is read as the column's own; SQLite's temporal values,
  text or milliseconds, are read untyped. None of these reads is refused on any of
  the nine tested databases.
- **`PagedList` and `PagedQuery` are single classes in common code.** The
  `AbstractPagedList` / `AbstractPagedQuery` bases and the per-platform subclasses
  that repeated every fluent method with a covariant return type are gone; the
  fluent methods are declared once and return `PagedList<T>`.
- **Several sorted facets are listed in the `ORDER BY` in the order they were
  sorted**, whether through `sort(path, direction)` or `facet.sort`; changing the
  direction keeps a facet's position, clearing and sorting it again puts it last.
  `saveState` keeps that order and `restoreState` restores it. A `PagedQuery`
  follows the order of the sorts in the `PageSpec`.
- **Enum facet values show display names.** Filter values (plain, counted and
  `PagedQuery.filterValues`) of an enum facet returned the stored database
  values (`10`, `99`, ordinals) instead of the display names the docs promise.
  They now map every stored value back through the facet's display-name map
  (`HumanReadable.displayName` or the enum name for an auto-built map, the keys
  of an explicit map); a stored value missing from the map is shown as is.
- **annproc: every property is a column, explicitly not one, or a compile
  error.** The annotation processor generated a setter for every
  non-transient property, so an entity with a computed `val x get() = ...` or
  any other `val` produced a registrar that did not compile ("'val' cannot be
  reassigned"). Now:
  - a property without a backing field and without a delegate is not a column
    (with a warning when it carries a column annotation), and neither is one
    marked `@Transient` / `@delegate:Transient`;
  - a mutable property is a column, whatever it delegates to, assigned through
    its setter;
  - a read-only property is a compile error: a `val` ("must be a var (or use
    by db())"), a `var` with a private or protected setter ("has no public
    setter"), `val x by db()`
    ("must be a var"), and any other read-only delegate such as `by lazy`
    without `@delegate:Transient` ("mark it @delegate:Transient, or make it a
    var ... by db()").
  JVM reflection, which needs no generated setter, maps read-only properties
  itself (see Annotations).
- **`@Entity(name)` is the table name under JVM reflection too** when there is
  no `@DbTable(name)` or `@Table(name)`, as in JPA and as the annotation
  processor already did. Before, reflection ignored it and derived the table
  name from the class name.
- **Loading a shadow reference holds a lock of the entity's own**, created when
  the first load needs it and dropped once the entity is loaded, so a loaded
  entity carries none; never the entity's monitor, which user code may hold,
  and which on the JVM pins a virtual thread across the load. The groups that
  batch sibling and `lazyDetails` loads lock the same way. One implementation
  on every target. The loaded flag is a plain private
  volatile field instead of an atomicfu atomic, so it is serialized with its
  value on Android too, where the atomicfu transformation does not apply. It
  has no accessors, so bean-property tools (Jackson, JAXB defaults) ignore it,
  but tools that read every non-transient field (Gson, JAXB with
  `XmlAccessType.FIELD`, Kryo) see `_isHydrated`; exclude it there if needed.
- **A read-only property backed by a delegate other than `db` is rejected
  under JVM reflection.** A `val x by lazy { }` that is not marked
  `@delegate:Transient` has nowhere to store a loaded value, and failed on
  every load. The class now fails when its metadata is built with "uses a
  delegate and cannot be mapped to a column: mark it @delegate:Transient or
  use by db()".

- **Page bounds are bound as parameters.** The paged `SELECT` of `PagedList`,
  `PagedQuery` and of filter values wrote the bounds into the SQL, so every page was
  a different statement: a hard parse per page on Oracle and a statement cache miss
  on every database. The bounds are now `?` placeholders and every page runs the
  same statement.

### Fixed
- **kotlinx-datetime values keep their wall time on the JVM.** A `LocalDateTime`,
  `LocalDate` or `LocalTime` went to and from `java.sql.Timestamp` / `Date` / `Time`
  through epoch milliseconds anchored at UTC, while those classes hold the wall time
  in the JVM's zone: a value was written and read shifted by the zone's offset, so a
  row written from the JVM read differently on native, and a value written by the
  database (a literal, another client) read wrong. The same held for a `java.time`
  wall-clock type read from a column of another kind (a `LocalDateTime` from a `DATE`
  on PostgreSQL) and for `java.util.Date`. Every pair between the `java.sql` types
  and a wall-clock type now converts the wall time itself.
- **Temporal text reads as a wall time on the JVM.** A temporal value kept as text
  (SQLite) is parsed with a space or a `T` between date and time, as a date alone or
  as a time alone, and without an offset as a time in the JVM's zone, as a timestamp
  column is read; `java.sql.Time`, `LocalDateTime` from a date, `Instant`,
  `OffsetDateTime` and `ZonedDateTime` failed on such text, and `java.sql.Timestamp`
  from a date read 12:00 UTC.
- **A double reads as its shortest decimal.** `BigDecimal` from a `DOUBLE` column was
  `0.1000000000000000055511151231257827...` for `0.1` on the JVM, and
  `0.10000000000000001` on native, where the drivers rendered doubles as text with
  17 digits; text and decimals of a floating point value are now the shortest that
  read back as it.
- **Native drivers read the fraction of a second from text.** `.123` was read as
  123 microseconds by SQLite, and by MariaDB and every driver's text fallback.
- **PostgreSQL on native reads a date or a time from a timestamp column**, and a
  timestamp from a date column; the time came from the timestamp's microseconds since
  2000 and failed, the date from its binary value parsed as text.
- **Temporal columns read as ISO text on native**: Oracle's `DATE` and `TIMESTAMP`
  came back `NULL`, PostgreSQL's `DATE`, `TIME` and `TIMESTAMP` as their raw binary
  bytes, and SQL Server's as `Mar 15 2024 12:00:00:AM`; all now read as
  `2024-03-15 13:45:30.123`, as the other drivers render them.
- **A `java.util.Date` is read as one**, not as the `java.sql.Date` the driver gives
  for a `DATE` column, whose `toInstant()` throws.
- **Android binds query parameters with their type.** A `SELECT` sent every
  parameter as text, which SQLite compares as greater than any number wherever no
  column affinity converts it: the pages of a list paged by `ROW_NUMBER` came back
  empty, as did conditions such as `COUNT(*) > ?`, and a `NULL` parameter was the
  empty string. An ionspin `BigDecimal` was bound as `1.0E+2` rather than `100`, so
  it did not match the text SQLite keeps for a decimal column. A missing table or
  another plain SQLite error now carries its error code.
- **Native targets bind and read an empty `ByteArray`.** Binding one failed on
  every native driver with "Bind failed", and SQLite and SQL Server read a stored
  empty blob back as `null`.
- **SQL Server on native targets keeps empty strings and blobs.** db-lib sends a
  parameter of length 0 as `NULL`, so `""` and an empty `ByteArray` were stored as
  `NULL`, and an empty string was read back as `null`. Empty values are now written
  into the statement as literals, as `NULL` already was.
- **A sequence fills a primitive key.** `create` asked the declared sequence only
  for a `null` key, so an `Int` or `Long` key, which starts at `0`, was inserted as
  `0` and a second row failed on the duplicate key. A key equal to `0` now takes the
  sequence's value.
- **`SingleAggregator` has Java overloads without the alias.** `sum`, `avg`, `min`,
  `max`, `count`, `countDistinct` and `raw` needed an explicit `null` alias from
  Java, unlike `MultiAggregator` and `PagedAggregator`.
- **kdbc on JVM returns the requested type when the driver refuses it.** When a
  driver's typed `getObject(index, Class)` throws, the value is read untyped; it was
  then returned as the driver gave it (a `String` for an `Int` request) instead of
  converted, as it is when the typed read succeeds. A type kdbc has no converter
  for is still returned as read.
- **Grouped `lazyDetails` loading matches decimal keys of any scale.** The
  grouped children query keyed its parents by their id value, so a parent
  loaded with a `DECIMAL(12,2)` key (`100.00`) was not found by the key read
  back through the child's integer column (`100`) with `java.math.BigDecimal`,
  and every parent silently fell back to a query of its own. The parents are
  now keyed as batch hydration keys them, equal decimals being one key.
- **Annotations of a primary constructor parameter are found under reflection
  when a secondary constructor repeats the parameter.** The annotations of a
  property declared in the constructor were taken from the first constructor
  that has a parameter of that name, so a secondary constructor repeating it
  without annotations hid `@DbField(primaryKey = true)` of the primary one and
  the entity had no key. Every constructor that declares the parameter now
  contributes, the primary one first.
- **Generated aggregate aliases fit the database's identifier limit.** An
  aggregate without an explicit alias got one derived from its path, up to 46
  characters, which Oracle before 12.2 rejects past 30 (`ORA-00972`) and
  PostgreSQL truncates past 63. `SqlDialect.maxIdentifierLength` now gives the
  limit, and a longer generated alias keeps its beginning and ends with a hash
  of the whole of it, so it stays distinct and stable. Explicit aliases are
  unchanged.
- **`selected` works on self-referencing entities.** The clause that puts the
  selected entity first named the primary key without its table, so a paged list
  that joins an entity to its own table (a parent reference) failed with
  "ambiguous column". The key is now qualified with the root table.
- **Generated registrars of many entities compile.** The registrar written by
  annproc (and by the Gradle plugin) registered every entity in one
  `register()` method, which a project of a few hundred entities pushes past
  the JVM limit of 64 KB per method ("Method too large"); splitting it into
  methods alone then hits the limit of the constant pool of one class. Each
  entity and each enum now registers in its own function, an entity's
  properties are built in chunks of 100, and the functions are spread over
  `internal object <Registrar>PartN` classes of at most 1000 properties each,
  which `register()` calls in turn. Measured on 400 entities of 17 columns:
  about 14,000 constants per part class and no method above 1 KB.
- **`val x by db()` is rejected under JVM reflection when the class is first
  used** ("is a val by db(): it must be a var to be loaded"), instead of
  failing on every load with "is not mutable".
- **No half-loaded entity seen by another thread.** A shadow reference and its
  batch siblings were flagged loaded before their row was read, and the flag
  was checked without a lock, so a second thread reading the same entity or a
  sibling during the load got empty fields. An entity is now flagged loaded
  only after its fields are filled; meanwhile it is in a transient loading
  state, in which the loading thread passes (its own setters) and every other
  thread waits for the load. An entity serialized during a load comes back
  unloaded.
- **Generated registrar escapes names.** annproc wrote column, table and
  sequence names into the generated Kotlin as plain string literals, so a name
  containing `$` (read as a template), `"` or `\` produced code that did not
  compile or held the wrong name. Every string in a generated literal is now
  escaped, in annproc and in the Gradle plugin's generator, with control
  characters as `\uXXXX`; other characters, such as Greek letters, are kept.
- **A failed lazy load is retried.** A shadow reference, its batch siblings
  and a `lazyDetails` property were marked loaded before their query ran, so a
  failed query (a dropped connection, a timeout) left them loaded with empty
  fields or an empty list for good. They are now marked loaded only when the
  load succeeds, and a failure puts the whole batch back unloaded, so the next
  access queries again. A reference whose row does not exist (a foreign key
  pointing nowhere) fails alone and on every access, while the valid
  references loaded in the same batch stay loaded. A sibling batch also uses the Stormify instance the
  trigger resolved (its own or the default), where it used to return without
  loading anything when the trigger had none attached.
- **`lazyDetails` serves results larger than one batch.** A result's rows
  shared one grouped query, limited to the first 32 parents, and the cached
  result answered every other parent with an empty list, without error, even
  the parent that asked first. A parent not yet covered now triggers its own
  batch of up to 32 uncovered rows, so every parent gets its children, as the
  References guide already described. A fetched slice is dropped from the group
  once its parent takes it, so the group no longer keeps the children of the
  whole result in memory for as long as any one row lives. Forming the batches
  walks the result once in total, not once per batch.
- **Paged constraints are parenthesized.** A constraint set through
  `setConstraints` is now wrapped in parentheses (closing on a new line, so a
  constraint ending in a `--` comment keeps the filters) before the facet filters are
  ANDed to it. A constraint such as `a = ? OR b = ?` used to become
  `a = ? OR b = ? AND <filter>`, so the filters applied only to the last
  operand and rows outside the filter leaked into the page, the count, the
  filter values, the aggregates and the stream.
- **Primary key breaks sort ties in paged queries.** Every primary key column
  is now appended to the `ORDER BY` of a paged list or paged query after the
  facet sorts, unless a facet already sorts on it. Before, a sort on a
  non-unique column left the order of equal rows to the database, so a row
  could appear on two pages or on none. Entities with a composite key no
  longer need an explicit facet sort: they are ordered by all key columns,
  and only an entity without any primary key still throws
  `IllegalStateException`.
- **Filter values and aggregates over a foreign key path join their tables.**
  `getFilterValues()`, `withCounts()`, `PagedQuery.filterValues` and the
  aggregators (`countDistinct("city.country.name")` and the rest) now emit the
  `LEFT JOIN` chain of the path they read even when no facet filters or sorts
  on it. Before, the join tree only held the paths with an active filter or
  sort, so these queries referenced a table alias that was never joined and
  failed.
- **Filter values handle SQL `NULL`.** `getFilterValues()` and
  `PagedQuery.filterValues` threw "selected column is NULL" as soon as the
  column held a `NULL`, and their `size`/`total` (a `COUNT(DISTINCT)`) left the
  `NULL` group out while `withCounts()` listed it as `""`. The `NULL` group is
  now one value in every view: counted in the size, always ordered last on
  every database, and shown as the configured `FilterSyntax.nullToken`, so
  choosing it as the facet filter selects the `NULL` rows.
- **Enum facets on `enumAsString` fields compare names.** The map an enum
  facet builds for itself held the ordinal / `DbValue` even when the field is
  stored as its name (`@DbField(enumAsString = true)`), so a filter compared a
  text column with a number: no rows on SQLite, `ORA-01722` on Oracle. The map
  now holds the enum name for such fields.
- **`FilterSyntax.wildcard` is honoured.** The text filter always treated `*`
  as the wildcard, whatever `wildcard` was configured to. The configured
  character is now the wildcard, `*` becomes a literal when another character
  is chosen, and a wildcard that is itself a `LIKE` metacharacter (`%`, `_`)
  works as a wildcard instead of being escaped. The default (`*`) is unchanged.
- **A null token without letters works on numeric and temporal facets.** A
  `FilterSyntax.nullToken` such as `--` or `―` has no letters, so on a
  numeric, date, time or timestamp facet it took the operator shortcut and was
  parsed as a value, matching nothing. The token alone now gives `IS NULL` and
  the token after the NOT operator (`---`, `- --`) gives `NOT (... IS NULL)`;
  negative numbers and dates are unaffected.
- **An empty or blank filter is no filter.** `Facet.filter = ""` (or only
  spaces), and the same value in `PageSpec.filters`, produced `1 = 0` for text
  and enum facets, an empty page for the others, and failed on a facet that is
  not filterable. It now clears the filter: the facet reads back `null` and the
  spec entry is skipped.
- **Custom facet converters may put `?` in literals.** The check that a
  converter pushed one argument per placeholder counted every `?` character,
  so a fragment such as `col = 'Who?'` was rejected. It now uses the same
  scanner as statement binding, which skips string literals, quoted
  identifiers and comments.
- **Library bookkeeping is no longer a JavaBean property.** The owning
  Stormify instance, the details group and the sibling group of an
  `AutoTable`/`StormifyEntity` compiled to public getter/setter pairs
  (`get_stormify$stormify()` and so on), which `java.beans.Introspector`
  and every bean-driven framework built on it reported as properties of each
  entity. They are now private transient fields; the accessors the library
  uses are synthetic (not callable from Java source) and named outside the
  get/set/is convention, so they are neither bean properties nor public Java
  API. Kotlin/Native is unaffected.
- **Decimal keys match whatever their scale.** Batch hydration of shadow
  references keyed rows by the key's `toString()`, so a `BigDecimal` key read
  as `100` on the FK side and `100.00` on the key side (an integer FK column
  pointing at a `DECIMAL(12,2)` key on PostgreSQL) never matched and the whole
  group failed with "No data found". Keys of `java.math.BigDecimal` and the
  ionspin `BigDecimal` now compare by value. The per-result reference cache
  also converts the FK value to the referenced key type first, so the same row
  reached through FK columns of different types is one reference.
- **Native stored-procedure OUT values keep SQL `NULL`.** On Kotlin/Native a
  numeric `Sp.Out`/`Sp.InOut` whose procedure left it `NULL` read back as `0`,
  while the JVM returned `null`. The native callable statement now returns
  `null` for a `NULL` OUT value of any type.
- **Read-only properties with a backing field are loaded under JVM
  reflection.** A `val`, a Kotlin `var` with a private or protected setter, or
  a Java field without setter could not be filled from the database ("Property
  is not mutable"). They are now loaded into their field and written by
  INSERT and UPDATE from that same field, not through the getter, so an
  UPDATE after a load writes back exactly the value the database holds, even
  through a custom getter that transforms it. A `val` primary key works too.
- **No transaction registry left on JVM threads.** The per-thread stack that
  tracks the active transaction was created on first lookup, so every thread
  that ever ran a query kept an empty stack in its `ThreadLocal` map. On an
  application server that value pinned the web application's classloader after
  undeploy. The stack is now created only when a transaction starts and removed
  when the outermost one ends, and a lookup outside any transaction leaves no
  entry behind (`ThreadLocal.get()` stores an empty entry, which is removed).
- **`@JoinColumn(insertable, updatable)` honored by JVM reflection.** Entities
  discovered through reflection read these flags only from `@Column`, so a
  read-only association next to its raw foreign key column put the column twice
  in INSERT and UPDATE. The annotation processor already read them.
- **A column mapped as both a value and a reference reads correctly.** When a
  plain property and a reference shared one column, the reference entity was
  handed to the plain property as well, and the conversion recursed until the
  stack overflowed. Each property now receives its own form of the value.
- **Stormify and JPA annotations on one property are merged the same way by
  reflection and by the annotation processor.** Reflection let a `@DbField`
  with default values override `@Id`, `@Column(insertable/updatable = false)`
  and `@Enumerated(STRING)`. The annotation processor let whichever annotation
  came last win, so `@Column` without a name could erase the name given by
  `@DbField`, and the table name depended on the order of `@Table` and
  `@Entity`. It also ignored `@GeneratedValue(strategy = IDENTITY)`. Both paths
  now take the name from the first annotation that sets one, set a flag such as
  the primary key if any annotation sets it, exclude a column from INSERT or
  UPDATE if any annotation excludes it, and pick the table name from
  `@DbTable`, then `@Table`, then `@Entity`.
- **`@SequenceGenerator` uses `sequenceName`.** Both JVM reflection and the
  annotation processor took the sequence from `name`, which in JPA only names
  the generator, so an entity whose generator and sequence names differed drew
  its keys from a sequence that does not exist. The sequence is now
  `sequenceName`, and `name` is used only when `sequenceName` is empty, so
  entities that rely on the old behavior keep working.
- **SLF4J detection leaves `System.err` alone.** The logger checked for an SLF4J
  backend by initializing SLF4J with `System.err` temporarily replaced, to hide
  the warning SLF4J prints when it has no backend. Replacing a process-wide
  stream is visible to every other thread, which on an application server can
  lose their error output. The logger now looks for a service provider, the
  `slf4j.provider` property, or a 1.x static binder before touching SLF4J.
  When there is none, SLF4J is never initialized and prints nothing. When
  there is one, SLF4J is initialized and its own messages go to `System.err`
  as usual: in particular SLF4J 2.x with only a 1.x binder on the classpath
  ignores the binder, prints its warning, and falls back to NOP. A NOP backend
  is recognized by its factory, instead of by the name of a test logger, and
  rejected, so the logger then uses the next framework.
- **Computed properties are not columns under JVM reflection.** A property with
  no backing field and no delegate, such as `val upper get() = name.uppercase()`
  or a `var` whose custom getter and setter use no field, was mapped as a column, so every INSERT, UPDATE and read of the entity named a
  column that does not exist. It is now skipped. A delegated property marked
  `@delegate:Transient` (for example `by lazy`) is now treated as transient,
  since its delegate field is.
- **The Gradle plugin is published.** The release pipeline staged every
  module except the Gradle plugin, so `id("onl.ycode.stormify")` resolved from
  no repository. The plugin and its marker now go to Maven Central with the
  other artifacts, signed like them, where the Gradle Plugin Portal finds them.
- **The Gradle plugin builds on recent Gradle.** Gradle 9.7 ships kotlin-stdlib
  2.4, whose metadata the Kotlin 2.2 compiler of the plugin refused to read, so
  the plugin module did not compile there. The plugin runs on the stdlib of
  the Gradle that loads it, and now compiles against it on any Gradle 9.
- **A transaction rethrows the exception of its block unchanged.** The block's
  own exception came out wrapped in an `SQLException`, so callers had to unwrap
  `cause` to tell it from a database error, unlike `withConnection { }`, which
  already let it through. Both scopes now behave the same.
- **Cancelling a coroutine stops its query on the JVM.** `Connection.cancel()`
  did nothing on the JVM, so cancelling the coroutine of a suspend transaction
  left its statement running to the end while the coroutine waited for it. The
  JDBC connection now cancels the statement it is running, until the statement
  returns or, for a query, until its result set is closed.
- **Cancelling a coroutine stops its query on SQL Server native.** The FreeTDS
  driver had no cancel. It now asks db-lib, through its interrupt check, to stop
  the statement it waits for; db-lib checks about once a second.
- **Cancelling a coroutine stops its query on MySQL native with Oracle's client
  library.** `libmysqlclient` has no `mariadb_cancel`, so the cancel did nothing
  there (the macOS Homebrew `mysql` setup, among others). It now opens a
  connection of its own and sends `KILL QUERY` for the running connection, as
  Connector/J does; with `libmariadb` it uses `mariadb_cancel` as before.
- **A cancelled suspend transaction counts as cancelled, not failed.** The
  failure of the statement the cancel interrupted came out as an
  `SQLException`, so the cancelled coroutine failed and took its parent scope
  down with it. It now ends in a `CancellationException`. A block that ended
  normally after its coroutine was cancelled was committed; it is now rolled
  back.
- **The logger types are on the compile classpath of a JVM or Android consumer.**
  `stormify` and `kdbc` declared the logger module as a runtime dependency,
  although `Stormify.logger` takes its `Logger` type, so setting a logger did
  not compile without adding `onl.ycode:logger` by hand.
- **`NamingPolicy.CAMEL_CASE` and `StormifyLifecycle.clear()` from Java**
  compile as the docs write them, without `INSTANCE`.
- **No empty test holder in a project without test entities.** On a plain
  `kotlin("jvm")` or Android project, the plugin generated an empty
  `TablesTest` into the test source set even when no test source declared an
  entity. Gradle 9 then saw test sources with no tests in them and failed the
  `test` task, and so `gradle build`. Nothing is generated for the test source
  set until it declares an entity.

- **Calls without an instance escaped the enclosing transaction.** Inside
  `other.transaction { }`, `entity.create()`, `findById<T>()` and the lazy load of an
  entity no instance read ran on the default instance, on a connection of their own,
  outside the transaction, so a rollback left their writes in place. They now use the
  instance of the innermost transaction or connection scope, then the default.
- **A constraint binds a `null`**: `setConstraints` / `constraints` take `Any?`.

### Documentation
- **Negated filter terms and `NULL`.** The PagedList guide states that `-foo`
  also excludes rows where the column is `NULL`, as SQL does, and shows
  `-foo OR NULL` to keep them.
- **Nested transactions.** The transactions guide no longer says that the outer
  block "still executes" after a nested failure: the nested call rolls back to
  its savepoint and still throws, so the outer block continues only if it
  catches the failure.
- **Java 8.** The installation guide lists what Java 8 and Java EE 7 projects
  need (matching Kotlin runtime, a JDBC 4.2 driver) and how to replace the
  Java 9 collection factories used in the examples.

## [2.6.0] — 2026-07-29

### Added
- **Batched `lazyDetails` loading.** Reading a `by lazyDetails()` property across
  the rows of one result now issues a single grouped query for every row's
  children instead of one query per row — the classic N+1 that turns a fast
  endpoint slow as the page grows. Rows of a result are marked as belonging
  together, and the first delegate asked fetches the whole group's children and
  hands each row its own slice. Applies to whole-result reads (`read`,
  `findAll`, paged queries); streaming reads are deliberately untouched, since
  their rows are never all in hand at once. The plain `getDetails`/`details()`
  path is unchanged: it re-queries on every call by contract.
- **Cursor API for row-by-row streaming.** Transparent streaming across the
  KDBC drivers (JDBC, native Postgres, MariaDB, Oracle) with per-driver
  dispatch — large result sets can be processed without materialising the
  whole list. Per-driver `cursorFetchSize` defaults are tuned to match each
  backend's natural batch size.
- **`java.time` and Kotlin UUID scalars** registered out of the box in
  `TypeConversion`: `LocalDate`, `LocalDateTime`, `Instant`,
  `OffsetDateTime`, `ZonedDateTime`, `kotlin.uuid.Uuid`, and
  `java.util.UUID` round-trip through the column plan without manual
  converters.
- **Benchmark suite** under `benchmarks/` comparing Stormify against JPA
  across CRUD and read-heavy scenarios, runnable on JVM and native targets.
- **Schema-sync headless modes** — `--export-sql` and `--export-kt` flags
  with category and glob filters, suitable for CI and scripted use with no
  TUI required.
- **Schema-sync packaged installers** — AppImage on Linux, ZIP on Windows,
  signed + notarized `.app` inside a `.tar.gz` on macOS; attached to a
  draft GitHub release on tag push.
- **Schema-sync TUI on Windows** renders natively against the Windows
  console (no MinTTY required), with assorted reliability fixes around
  focus/exit-stack handling.
- `AutoTable.hydrate()` — `protected` at-most-once lazy-load helper.
  Subclasses that hand-write getters/setters (typically Java) call this to
  trigger the same lazy-load behaviour that the Kotlin `db` delegate
  applies automatically.
- **`SuspendStormify.withConnection { }`** — a pooled-connection scope
  without transaction semantics. Until now the only way to borrow from the
  suspend pool was `transaction { }`, which forced BEGIN/COMMIT (and its
  `SQLException` wrapping) onto plain reads. `withConnection` borrows a
  pooled connection in auto-commit mode, publishes it to the ambient
  blocking API exactly like a transaction does, and propagates exceptions
  **unchanged** — application exceptions no longer evict healthy
  connections, and only coroutine cancellation does. The two scopes nest
  in every combination: `withConnection` inside either scope reuses the
  ambient connection, `transaction` inside `transaction` opens a savepoint
  (unchanged), and `transaction` inside `withConnection` runs a full
  BEGIN/COMMIT cycle on the borrowed connection.
- **`stormify.suspending` shared pool.** `suspending` is now a lazy
  property on `Stormify` (tuned by the new `poolConfig` constructor
  parameter), so the whole process shares one pool by default. The
  `suspending(config)` factory extension is removed — code that needs a
  separate pool uses the new public `SuspendStormify(stormify, config)`
  constructor. `Stormify.closeSuspending()` closes the shared pool at
  shutdown without creating it when it was never used.

### Changed
- **`AutoTable` auto-hydration is now ownership-based.** A user-constructed
  entity is never auto-loaded from the database. Library-constructed shadow
  references (FK stubs produced by a parent's read) continue to auto-hydrate
  on first `db` property access.
- `AutoTable.markPopulated()` was renamed to `AutoTable.markHydrated()` for
  vocabulary consistency.
- **Published libraries target JVM 8 bytecode**, broadening the set of
  runtimes that can consume them. `schema-sync` and the test/benchmark
  modules target JVM 11.
- The `schema-sync` demo now runs against a dedicated `stormify_demo`
  database, isolated from the conformance suite so the two no longer share
  state.
- **Android minimum is now API 26** (Android 8.0), the floor imposed by
  `java.time` usage in the shared JVM/Android source set. (The 2.5.x line
  had silently raised the floor from 21 to 28; 26 is the actual technical
  minimum and restores part of the lost device coverage.)
- **Suspend `transaction { }` now reports failures as `SQLException`**, the
  same contract the blocking API always had: the original throwable (from
  the database or from user code inside the block) is kept as `cause`.
  Coroutine cancellation is exempt and still propagates unwrapped.
- **`initSql` now accepts more than one statement**, separated by `;` and run
  in order on every freshly opened connection, so common setups no longer need a
  hand-written `DataSource` wrapper to apply more than one pragma
  (`initSql = "PRAGMA foreign_keys = ON; PRAGMA busy_timeout = 5000"`). Applies
  to `KdbcDataSource`, `JdbcDataSource` and `AndroidDataSource`.

### Fixed
- Reading a text or binary column into a numeric field no longer yields `0`
  on the native drivers and on Android. The C getters parse with
  `strtoll`/`strtod` and `Cursor.getInt` behaves the same way — both answer
  `0` for input they cannot parse and report no error, so a column of words
  read into an `Int` field silently became zero on those platforms while the
  same read failed on JVM. The numeric getters are now taken only when the
  column actually holds a number; otherwise the value is read in the
  column's own type and converted, which refuses what it cannot represent.
- Reading a numeric column into a `CharArray` works on every database.
  `TypeConversion` derives the `CharArray` conversions from the `String`
  ones, so anything with a text form has a character form.
- MySQL/MariaDB `BOOLEAN` columns (stored as `TINYINT(1)`) are reported as
  booleans by the native driver, matching both JDBC drivers.
- Paged-list and paged-query window counts no longer assume the driver hands
  back a `kotlin.Number`, and are converted through `TypeConversion`.
- Reflection-based entity discovery (Maven/plain-JVM projects without the
  annotation processor) again honors `javax.persistence.Column`
  (`name`/`insertable`/`updatable`) — it had been looking up a nonexistent
  `javax.persistence.Facet` annotation since 2.1.0.
- Batch `create()` no longer assigns a generated key to the wrong entity
  when the single item needing a database-generated id is not the last in
  the batch; the key is now read immediately after that item's own insert.
- JDBC typed `getObject` calls no longer receive primitive Java classes
  (`boolean.class` & friends) when the requested `KClass` originates from
  `typeOf<T>()` — drivers that reject primitive class tokens now get the
  boxed type, restoring proper typed conversions (e.g. SQLite
  `TEXT '1'` → `Boolean true`).
- Scalar reads whose selected column is SQL NULL now fail with a clear
  `SQLException` naming the target type and suggesting SQL-side handling
  (`COALESCE`), instead of the generic "Expecting type … but found null".
- `update()` / `delete()` with a null primary key now fail immediately with a
  clear `SQLException` instead of silently affecting zero rows.
- Batch `create()` with sequence-generated ids now fails with a clear
  `SQLException` when the database returns fewer sequence values than
  requested, instead of an `IndexOutOfBoundsException`.
- An empty collection passed as a query parameter now fails with a clear
  `SQLException` ("cannot be expanded into an IN list") instead of producing
  invalid `IN ()` SQL and a driver-level syntax error.
- A cursor query's `fetchSize` no longer leaks into subsequent non-cursor
  uses of the same SQL through the prepared-statement cache; the driver
  default is restored when the statement is returned to the cache.
- `update()` on an entity with no updatable fields now fails with a clear
  `SQLException` instead of emitting invalid `UPDATE … SET  WHERE …` SQL.
- The annotation processor and the Gradle plugin's source generator now report
  a clear error at build time when two entities, two enums, or an entity and
  an enum share the same simple name in different packages, instead of
  emitting colliding declarations that fail with a cryptic "redeclaration"
  or "conflicting import" error.
- Unmatched-column diagnostics and `@DbField` KDoc no longer refer to columns
  as "Facet" — a leftover of an old rename that pointed users at the
  unrelated `biglist.Facet` API.
- Suspend `transaction { }` no longer leaks the internal
  `HealthyConnectionException` marker to callers when an exception crosses
  a dispatcher boundary; the connection-health signal is unwrapped layer
  by layer at the pool boundary.

### Removed
- `PagedList.add(entity)` / `PagedList.remove(entity)` — misleading names
  inherited from the original Java API: they never touched the database, they
  merely set/cleared the selection (`remove` even ignored its argument). Use
  the `selected` property directly.
- `PagedList.set(index, element)` — mutated only the cached page in memory
  while looking exactly like `java.util.List.set`, suggesting persistence that
  never happened; the change vanished silently on the next `refresh()`. To
  show updated data, persist via `update(entity)` and call `refresh()`.
- `AutoTable.populate()` (the public direct-call API) and
  `Stormify.populate(entity)` / `StormifyJ.populate(entity)` (the
  manager-level loaders) were removed in favour of the single direct-call
  entry point `Stormify.refresh(entity)` / `StormifyJ.refresh(entity)`,
  equivalent to JPA's `EntityManager.refresh(entity)`. Every call performs
  a SELECT and overwrites the in-memory fields.

### Changed

  receiver. `transaction { ... }` now installs a thread-local active
  context, so CRUD calls work directly inside the block without the
  receiver. Nested transactions and savepoints behave the same as
  before.
- Tests moved into their own module for cleaner build separation.
- Pooled connections on native and Android are now bound to a
  long-lived single-thread dispatcher, giving consistent suspend
  semantics and reliable cancellation.
- Placeholder scanning is quote- and comment-aware: `?` inside string
  literals and SQL comments is no longer counted as a parameter, and
  list expansion respects the same rules.
- Normalized bind type coercions across all drivers; bind errors now
  include parameter index and value context for easier debugging.
- Examples REST DB generator cleaned up.

### Removed
- `TransactionContext` class and its receiver-style extension methods
  — superseded by the ambient transaction registry. Code that
  previously took `TransactionContext` as a receiver or parameter
  must be updated to use the ambient context instead.

## [2.0.0] — 2026-04-14

First Kotlin Multiplatform release. This is a major version bump with
breaking changes; see [Migration_V1_to_V2](docs/src/Migration_V1_to_V2.md).

### Added
- **Kotlin Multiplatform targets**: JVM, Android (API 21+), Linux x64 /
  ARM64, Windows (mingwX64), macOS (Apple Silicon + Intel), and iOS
  (device, simulator Intel, simulator Apple Silicon).
- **Native database drivers** via a unified `libkdbc` C library behind a
  single vtable: SQLite, PostgreSQL (libpq), MariaDB/MySQL (libmariadb),
  Oracle (ODPI-C), MS SQL Server (FreeTDS). No JVM, no JDBC.
- **Suspend transaction API** (`SuspendStormify`) with a built-in
  coroutine-aware connection pool, prewarm, validation, background
  cleanup, graceful shutdown, and coroutine cancellation wired to native
  database cancel primitives (`kdbc_cancel`).
- **Stored procedure API** (`Sp`) with IN / OUT / INOUT parameters for
  PostgreSQL, Oracle, MSSQL, MariaDB, and MySQL.
- **Enum support** with ordinal, custom `DbValue` integer, and string
  storage modes; case-insensitive matching.
- **PagedList** and **PagedQuery** for UI grids and stateless REST
  endpoints — filters, sorting, FK traversal, aggregations, facet
  counts, streaming `forEach` over very large result sets, and
  save/restore state.
- **Annotation processor** (`annproc`) based on KSP to generate
  `TableInfo` registrations at compile time (required for native and
  Android; optional on JVM).
- **Android** support with Robolectric test coverage and a working
  Compose example app.
- **Transaction results**: `transaction { ... }` returns the block's
  value.
- Reference paths and type-safe `lazyDetails` for Java consumers.
- Multi-encoding test suite including Oracle 11g with Greek
  `EL8ISO8859P7` charset.
- Boolean bindings across all drivers.

### Changed
- Converters moved from `stormify` into `kdbc`; binary `ionspin`
  conversions; converter classes under `onl.ycode.kdbc.converters`.
- Examples are published as an external repository
  ([stormify-examples](https://github.com/teras/stormify-examples)) and
  linked via a git submodule.
- Library compiles to Java 8 bytecode for consumer compatibility; built
  with JDK 11 / tested with JDK 17.
- Single macOS-based publish workflow replaced with a multi-host CI
  that aggregates platform-specific klibs into one KMP deployment.

### Fixed
- Oracle 11g cancel hang — skip rollback/close after `OCIBreak` (no
  `OCIReset` in ODPI-C).
- Reflection, reference resolution, and batch update for JVM entity
  handling.
- `kdbc_stmt_reset` now clears batches, OUT-parameter values, and
  generated-key state.
- UUID generated keys for PostgreSQL and MSSQL.
- Android suspend transaction cancellation; added scoped `asDefault`.
